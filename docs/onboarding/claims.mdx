A **claim** (`clm_...`) is a fact about a [person](/docs/onboarding/persons), such as their residence or their identity. Its values are **versions** (`clmv_...`): every time the value changes, we add a version and keep the ones before it. Applications validate against claims.

<Note>
This page describes API version `2026-11-04` and later. If you pin `2026-11-01` or earlier, claim routes return one row per value instead; see [older API versions](#older-api-versions).
</Note>

## Claims and versions

A person has at most one claim of each `claim_type` that applies. Each claim holds its versions, numbered from 1 in the order they were written.

| Term | Meaning |
|---|---|
| Latest version | The highest-numbered version, verified or not. Returned as `latest_version`. |
| Latest verified version | The highest-numbered version with `status: verified`, which can be the latest one. Returned as `latest_verified_version`, or `null` when no version is verified. |
| `status` | `unverified` when we haven't checked the value against a verification source, `verified` once a check passed (`verified_at` is set). Verification isn't self-service: our checks set it. |
| `archived_at` | Set on a claim that no longer applies. See [archiving a claim](#archiving-a-claim). |

Versions are never edited. A newer value doesn't overwrite the old one, so you can always read what a claim held before.

## Writing a claim value

`POST /persons/{person_id}/claims` with the value as the body. `claim_type` tells us which claim you're writing. If the person has no claim of that type yet, we create it with version 1; otherwise we add the next version to it.

| Field | Description |
|---|---|
| `id` | The version's ID, prefix `clmv_`. |
| `number` | Its position in the claim's history, from 1. |
| `status` | `unverified` or `verified`. See [claims and versions](#claims-and-versions). |
| `data` | The value, in the claim type's schema. See [claim type reference](#claim-type-reference). |
| `verified_at` | When the value was verified, or `null`. |
| `sources` | Where the value came from. For your calls, the actor and OAuth client that made the call, and your `reference` if you sent one. |
| `claim` | The claim this is a version of, without its versions. |

### Writing the same value again

If the value you send equals the latest version, we don't add a version. We return the latest version as it stands, with your call added to its `sources` with `role: confirms`. Check `number` rather than assuming it went up.

### Avoiding lost updates with `based_on`

Send `based_on` with the version `number` you read. If someone else wrote a newer version since, we write nothing and return `409 claim_version_conflict`; read the claim again and retry. `based_on` and your own `reference` sit beside the value's fields in the body:

```bash
curl -X POST https://api.joinsophic.com/persons/per_m4k7r9s2/claims \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6c1f2e0a-residence-update" \
  -d '{
    "claim_type": "residence",
    "line1": "42 New Street",
    "postal_code": "EC2A 4RQ",
    "city": "London",
    "country_code": "GB",
    "based_on": 1,
    "reference": "crm-update-8812"
  }'
```

### Retrying safely

Send an `Idempotency-Key` header on writes. If you retry with the same key, for example after a timeout, we return the version the first attempt wrote or confirmed, and write nothing.

## Listing and retrieving claims

[`GET /persons/{person_id}/claims`](/api-reference/customers/list-claims-for-a-person) lists the person's claims that still apply, newest first. Each claim carries its `latest_version` and `latest_verified_version`.

```bash
curl "https://api.joinsophic.com/persons/per_m4k7r9s2/claims?claim_type=residence" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN"
```

| Query parameter | Values | Notes |
|---|---|---|
| `claim_type` | Any [`claim_type`](#claim-type-reference) | Optional. |
| `include_history` | `true`, `false` | Optional, default `false`. Set to `true` to get every version under `versions`, highest number first. |

```json
[
  {
    "id": "clm_r3s1d9",
    "claim_type": "residence",
    "person": "per_m4k7r9s2",
    "archived_at": null,
    "created_at": "2026-04-18T09:30:00Z",
    "is_archivable": false,
    "latest_version": {
      "id": "clmv_8q2w5e",
      "number": 2,
      "status": "unverified",
      "data": { "claim_type": "residence", "line1": "42 New Street", "line2": null, "line3": null, "district_county": null, "postal_code": "EC2A 4RQ", "city": "London", "country_code": "GB" },
      "verified_at": null,
      "sources": [ … ],
      "created_at": "2026-11-05T09:30:00Z"
    },
    "latest_verified_version": {
      "id": "clmv_1a7b3c",
      "number": 1,
      "status": "verified",
      "data": { "claim_type": "residence", … },
      "verified_at": "2026-04-19T11:00:00Z",
      "sources": [ … ],
      "created_at": "2026-04-18T09:30:00Z"
    },
    "versions": null
  }
]
```

Use `latest_version` to show what the person told you most recently, and `latest_verified_version` where you need a value that passed a check.

[`GET /persons/{person_id}/claims/{claim_id}`](/api-reference/customers/retrieve-a-person-claim) returns one claim, archived or not, and takes `include_history` too. [`GET /persons/{person_id}/claims/{claim_id}/versions`](/api-reference/customers/list-a-claims-versions) lists its versions, highest number first, each with its claim.

## Adding a version to a claim

[`POST /persons/{person_id}/claims/{claim_id}/versions`](/api-reference/customers/add-a-version-to-a-claim) writes a new value to a claim you name. It works like [writing a claim value](#writing-a-claim-value), including `based_on`, `reference` and `Idempotency-Key`. The value must be of the claim's type, and the claim must still apply; otherwise we return `400 claim_type_mismatch`.

## Archiving a claim

[`DELETE /persons/{person_id}/claims/{claim_id}`](/api-reference/customers/archive-a-claim) archives a claim that no longer applies, such as a registered address the entity has moved on from. We set `archived_at` and keep its versions, so you can still retrieve it by ID. It's no longer listed, and the next value of its type starts a new claim at version 1.

Some claims can't be archived, because a person can't do without them: `identity`, `nationalities`, `residence`, `tax_residencies`, `contact_details` and `registration`. Each claim tells you with `is_archivable`. Archiving one of these, or a claim that's already archived, returns `400 claim_archive_not_allowed`. To change one, write a new value instead. You can send `based_on` as a query parameter to refuse the archive if the claim moved on.

## Older API versions

Clients pinned to `2026-11-01` or earlier get the same data in the shape from before: one row per value, with the value's fields at the top level, `status` as `pending` or `verified`, `superseded_at`, `archived_at` and `lifecycle` per row, and `include_history` defaulting to `true`. A value written since 5 Nov 2026 is identified there by its version ID (`clmv_`). See [versioning](/api-reference/versioning) to move to `2026-11-04`.

## Claim type reference

Unknown fields are rejected. Dates are ISO-8601, country codes ISO-3166-1 alpha-2.

<Warning>
Most claim types are specific to natural or legal persons; `contact_details` is valid on both. Creating a claim whose `claim_type` isn't valid for the target's `person_type` returns `400 invalid_request` (e.g. `Claim type 'relationships' is not allowed on natural persons.`). See [claim creation errors](/docs/onboarding/errors#person-creation-errors).
</Warning>
