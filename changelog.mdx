<Update label="October 1, 2026" description="2026-10-01">
  ## Trading configuration and consistent order validation

  <Info>New API version `2026-10-01`. See [Versioning](/api-reference/versioning) to migrate.</Info>

  Instruments now describe their order rules in a single `trading_configuration` object, split into buy and sell. Quotes run the same checks as placement, so a quote fails exactly where the order it previews would. When a quoted order breaks a sizing rule, you get the quote back with the rule it breaks, so you can show your users what to change before they place it. Requests pinned to `2026-09-28` or earlier keep the legacy instrument fields and the previous error responses.

  **Breaking**
  - Instruments, wherever we return them (on their own or embedded in positions, orders, quotes, transactions, and valuations), no longer carry `minimum_trading_quantity`, `minimum_initial_cash_investment`, `required_cash_increment`, or `enforce_trading_rules`. Read the rules from `trading_configuration` instead:
    - `minimum_initial_cash_investment` is `trading_configuration.buy.min_initial_cash_amount`.
    - `minimum_trading_quantity` is `trading_configuration.buy.min_cash_amount`.
    - `required_cash_increment` and `enforce_trading_rules` have no replacement. We use null in the trading configuration when no rule applies.
  - [Get an order quote](/api-reference/trading/get-an-order-quote) returns `200` instead of `400` for an order that breaks a sizing rule: a quantity off the trading increment, a cash amount that buys less than one trading increment, or a minimum in `trading_configuration`. The quote carries its `estimate` as usual, with `is_placeable: false` and the rule in `blockers`. Placing the order as quoted still fails with the same error.
  - [Get an order quote](/api-reference/trading/get-an-order-quote) and [Place an order](/api-reference/trading/place-an-order) return `trading_rule_violated` instead of `invalid_request` when an order breaks a rule in `trading_configuration`. `context.rule` names the rule (for example `buy.min_initial_cash_amount`), with `context.required` and `context.actual`. `params` still points at the field the order was sized by.

  **Added**
  - `trading_configuration` on [instruments](/api-reference/catalog/retrieve-an-instrument), on every API version. `buy` carries `modes`, `min_cash_amount`, `min_initial_cash_amount`, `min_quantity`, and `min_initial_quantity`; `sell` carries `modes`, `min_cash_amount`, and `min_quantity`. A `null` minimum isn't applied, and a sell minimum never blocks selling a whole position. Cash amounts are in the instrument's trading currency.
  - `is_placeable` and `blockers` on every [order quote](/api-reference/trading/get-an-order-quote). Each blocker carries the `code` and `detail` placement would return, and a `context` with `rule`, `required`, `actual`, and `required_cash_amount`: on a cash buy, the smallest `cash_amount` (fees included) that meets every buy rule.
  - `trading_rule_violated` error code.
  - `insufficient_funds` and `insufficient_units` blocker codes on [order quotes](/api-reference/trading/get-an-order-quote). When a quote returns these blockers, the `context` tells you the balance check that failed: `available` and `requested` amounts, and the account `currency` (for funds) or the position's available units (for units). You can use this to prompt users to add funds or adjust their position size before placing the order.

  **Changed**

  These apply on every API version.
  - [Get an order quote](/api-reference/trading/get-an-order-quote) runs the same instrument and account checks as placement, so it can now return `instrument_not_trading`, `instrument_buy_only`, `instrument_sell_only`, `instrument_too_close_to_maturity`, `currency_not_supported`, `insufficient_units`, `buy_order_forbidden`, `sell_order_forbidden`, and `professional_trader_required`.
  - A `quantity` must be a multiple of the instrument's `trading_increment`, on quotes and orders. We reject a quantity off the increment rather than trimming it.
  - Cash buys are sized by rounding the quantity down to the instrument's `trading_increment` instead of to whole units. The quote's `estimate.quantity` now matches the quantity the order executes, including the price buffer we apply.
  - Buy minimums apply to the cash the buy invests, net of fees. Quotes for limit cash buys now check them too. Rollover orders are exempt.
  - We no longer enforce a cash increment on buys. On `2026-09-28` and earlier, `required_cash_increment` is always `0` and `enforce_trading_rules` is always `false`.
  - An order that sends both `cash_amount` and `quantity` is rejected with `invalid_param` on `quantity`. Previously, `quantity` silently took precedence.
  - Selling an instrument the account holds no position in returns `insufficient_units` with `context.available` of `"0"`.
  - `trading_increment` on instruments is returned at full precision (for example `"0.00010000"`) instead of rounded to two decimal places.
</Update>

<Update label="September 29, 2026" description="additions">
  ## Order validation error codes

  We've added new error codes to provide clearer feedback when orders conflict with instrument trading restrictions.

  **Added**
  - `instrument_buy_only` error code when you attempt to sell an instrument that only accepts buy orders.
  - `instrument_sell_only` error code when you attempt to buy an instrument that only accepts sell orders.

  **Changed**
  - `insufficient_units` errors report `context.available` as an exact decimal string (for example `"0.5"`) instead of a number rounded down to whole units.
  - [Get an order quote](/api-reference/trading/get-an-order-quote) errors for a cash buy that misses the instrument's minimum initial investment or cash increment now point at `body.cash_amount` instead of `body.quantity`.
</Update>

<Update label="September 28, 2026" description="2026-09-28">
  ## Redesigned earnings responses

  <Info>New API version `2026-09-28`. See [Versioning](/api-reference/versioning) to migrate.</Info>

  We've reshaped earnings (P&L) responses to provide a clearer picture of how earnings are distributed between market gains and FX currency movements, for accounts that hold investments or cash in currencies other than the account's base currency. Requests pinned to `2026-09-02` or earlier keep the previous flat field layout, without this breakdown.

  **Breaking**
  - [Retrieve account earnings (P&L)](/api-reference/performance/retrieve-account-earnings-p&l) returns `gross`, `fees`, and `net` at the top level, plus a `positions` block and a `cash` block. The flat `gross_*`, `net_*`, `realized_*`, and `unrealized_*` fields are gone. `net` is `gross` minus `fees`. `gross` is `positions.gross` plus `cash.gross`.
  - The realized/unrealized and capital/income split moved under `positions.attribution`, which separates an `investment` effect (price changes and income, with exchange-rate movements stripped out) from a `currency` effect (exchange-rate movements on the money invested in positions). Each effect carries `total`, `realized.capital`, `realized.income`, `unrealized.capital`, and `unrealized.income`, all in the account's currency. The `currency` effect is zero when everything is in the account's currency.
  - `position_earnings` is no longer included in the account response by default. Pass `include_positions` to get each position's earnings inline, as [Retrieve position earnings (P&L)](/api-reference/performance/retrieve-position-earnings-p&l) returns them.
  - The position response returns two views instead of one flat grid: `trading`, in the instrument's own currency, and `reporting`, in the account's base currency. `currency`, `cost_basis`, and `gross` now live inside each view rather than at the top level, and `gross_unrealized_percentage` is now `trading.unrealized_percentage`.
  - `trading.attribution` holds only an `investment` effect, since exchange rates play no part in the instrument's own currency. `reporting.attribution` holds both `investment` and `currency` effects, with each leg converted at the exchange rate of the day it happened rather than a single period-end rate. Summed over all positions, the `reporting` figures give the account's `positions` figures.

  To migrate a position response, map the old flat fields onto the `trading` view:

  | Before `2026-09-28` | From `2026-09-28` |
  |---|---|
  | `gross_total` | `trading.gross` |
  | `realized_capital`, `realized_income` | `trading.attribution.investment.realized.capital`, `.income` |
  | `unrealized_capital`, `unrealized_income` | `trading.attribution.investment.unrealized.capital`, `.income` |
  | `gross_realized` | `realized.capital + realized.income` |
  | `gross_unrealized` | `unrealized.capital + unrealized.income` |
  | `gross_capital` | `realized.capital + unrealized.capital` |
  | `gross_income` | `realized.income + unrealized.income` |
  | `cost_basis`, `currency` | `trading.cost_basis`, `trading.currency` |
  | `gross_unrealized_percentage` | `trading.unrealized_percentage` |

  The account response follows the same pattern, with `gross_total` becoming `gross`, `net_total` becoming `net`, and the four buckets living under `positions.attribution.investment` and `positions.attribution.currency`.

  **Added**
  - `account` on position earnings responses (from `2026-09-28`), the ID of the account holding the position.
  - `cash` on account earnings responses (from `2026-09-28`): what uninvested foreign-currency cash gained or lost from exchange-rate movements, as `cash.gross` and `cash.attribution.currency.total`. It isn't split into realized and unrealized.

  **Changed**
  - Account earnings totals now include exchange-rate gains and losses on uninvested foreign-currency cash, on every API version. On `2026-09-02` and earlier this means `gross_total` and `net_total` can differ from `gross_realized` plus `gross_unrealized` by that cash currency effect.
</Update>

<Update label="September 22, 2026" description="additions">
  ## Instrument client categories and deposit status tracking

  We now return client category information on instruments to support MiFID II compliance, and provide expanded deposit statuses for better visibility into their lifecycle.

  **Added**
  - `target_client_categories` on [instrument](/api-reference/catalog/retrieve-an-instrument) responses, returning an array of client categories (retail, professional per se, professional on request) the instrument is intended for.
  - New deposit statuses: `held`, `returning`, `returned`, and `cancelled`, providing better tracking of the deposit lifecycle.
  - `restricted` as a new instrument rollout stage.

  **Changed**
  - Fee charge `amount` field description now clarifies it reflects the notional the fee was priced on; it's null when the amount doesn't depend on a notional (as with flat fees).
</Update>

<Update label="September 2, 2026" description="2026-09-02">
  ## Redesigned order quote responses

  <Info>New API version `2026-09-02`. See [Versioning](/api-reference/versioning) to migrate.</Info>

  We've reshaped the [Get an order quote](/api-reference/trading/get-an-order-quote) response. Instead of one generic object for every quote, you now get a variant specific to the instrument and order mode you asked about, carrying only the economics that apply to that combination.

  **Breaking**
  - `POST /accounts/{account_id}/order-quotes` no longer returns a single generic `OrderQuote` object. It returns a union discriminated on `quote_type`, with one variant per instrument and order mode: `amc_market_cash`, `bill_market_cash`, `bond_fixed_coupon_market_cash`, `bond_zero_coupon_market_cash`, `etf_market_cash`, `etf_limit_cash`, `etf_market_quantity`, `etf_limit_quantity`, `mmf_market_cash`, or `sell`. Switch on `quote_type` before reading a quote.
  - The flat economics fields moved under an `estimate` object and dropped the `estimated_` prefix: `estimated_price`, `estimated_quantity`, and `estimated_cash` are now `estimate.price`, `estimate.quantity`, and `estimate.cash`. `fees`, `net_cash_amount`, `max_cost`, and `min_proceeds` moved under `estimate` too. Each variant only carries the fields that apply to it.
  - `instrument` is now the full instrument object instead of an ID string.

  **Added**
  - `order_type` on every variant, indicating whether the quote is for a market or limit order.
  - `currency` on every variant.
  - Instrument-specific economics in `estimate`: `yield`, `annual_income`, and `accrued_interest` for fixed income, plus `notional`, `cost`, `price_buffer_percentage`, and `asof` where they apply.
  - `reservation` object on every variant with what a placement would set aside: a cash amount vs a unit quantity (`amount`, `denomination`).
  - `created_at` on every variant.
  - `fee_breakdown` on every estimate, providing an itemized list of fees. Each line includes a `label` (the fee category), `display_name` (a human-readable name), and `amount` (the fee value in the quote's currency). The line amounts sum to the total `fees` exactly.
</Update>

<Update label="July 28, 2026" description="additions">
  ## OAuth token endpoint RFC 6749 compliance

  The `POST /auth/token` endpoint now returns RFC 6749-compliant error responses
  so you can distinguish between bad requests and authentication failures.

  **Added**
  - `401 Unauthorized` response for client authentication failures on [Issue an OAuth token](/api-reference/auth/issue-an-oauth-token), with an `OAuthErrorBody` payload following RFC 6749 §5.2.

  **Changed** (backwards compatible)
  - `400 Bad Request` response on `POST /auth/token` now uses `OAuthErrorBody` schema with `error` and `error_description` fields (RFC 6749 §5.2) instead of the standard error envelope.
</Update>

<Update label="July 22, 2026" description="additions">
  ## Identify the end person on each request

  When a call concerns an end person, send `Person-Id` so we can attribute the
  action for compliance. `Client-User-Id` is optional and helps with debugging.

  **Added**
  - `Person-Id` request header for our person ID (`per_…`) you're acting on
    behalf of. Send this whenever the request concerns an end person. See
    [Attribution](/api-reference/attribution).
  - Optional `Client-User-Id` request header for your own identifier of the
    same end user, for log correlation and support.
  - Error codes `person_id_too_long` and `client_user_id_too_long` when either
    header exceeds 255 characters.
</Update>
